# Media failure-fixture matrix

This matrix is deliberately separate from the 30 valid synthetic fixtures. It defines the Windows media cases that must fail cleanly during extraction and must never create a final `.vtt` file. The binary fixtures are generated or acquired only under their stated provenance, then checked into the internal test-artifact store; they are not silently regenerated by normal unit tests.

| Fixture ID | Intended input | Expected extraction result | Required assertion |
|---|---|---|---|
| `malformed-truncated.mp4` | An MP4 header followed by a deliberately truncated box payload | Failure | Error identifies unreadable/corrupt media; no temporary WAV or final VTT remains. |
| `no-audio-video-only.mp4` | Valid MPEG-4 container with exactly one video track and no audio tracks | Failure | Error states that no usable audio can be transcoded; no temporary WAV or final VTT remains. |
| `empty-audio-track.mp4` | Valid audio-only container whose decoded audio length is zero | Failure or header-only success, according to the observed Windows transcoder result | Record the observed behavior by architecture; never leave a partial VTT. |
| `unsupported-audio-codec.mp4` | Valid MPEG-4 container with an intentionally unsupported audio codec | Failure | Error is actionable and names media/transcoding; no temporary WAV or final VTT remains. |
| `valid-short-control.mp4` | Rights-cleared audio-only AAC MP4 with one short spoken utterance | Success | PCM is PCM16/16 kHz/mono and a valid VTT is committed atomically. |

## Collection rules

- Keep the source/provenance and SHA-256 for every binary in the release evidence store.
- Execute this matrix with the Windows media integration tests on both x64 and ARM64. It complements, and does not count toward, the synthetic 30-file corpus.
- Test cancellation separately at prepare/transcode/validation boundaries using the valid control fixture; verify the temporary directory is empty afterward.
- Do not use a malformed extension alone as an invalid-media test: every case above exercises the Windows media pipeline itself.

## Local Windows-native candidate generation

The companion corpus tool can create an opt-in local candidate matrix with deterministic technical provenance. It is never invoked by normal tests and refuses to overwrite any fixture or its sidecar:

```powershell
dotnet run --project tools/WinBulkTranscript.CorpusGenerator -- `
  --voice-id '<installed voice ID>' `
  --media-fixture-matrix C:\fixtures\win-bulk-transcript-media
```

The matrix root must be outside this repository's `test-assets` directory: it is opt-in evidence and must not masquerade as shipped test assets. The command writes all five named MP4s plus `media-fixture-matrix.provenance.json`. The valid control uses locally synthesized Windows speech; the no-audio file uses a native solid-colour video composition; malformed and unknown-codec inputs are bounded deterministic container transformations; and the empty-track input preserves one native AAC audio description while deterministically zeroing its movie/track/media durations plus `stts`, `stsc`, `stsz`/`stz2`, and chunk-offset entry counts (and any optional sample-reference tables). The writer rereads the completed file and the sidecar records the post-mutation structural proof, selected voice, host, construction details, and SHA-256 for every resulting file.

This is reproducible **technical** provenance, not a legal conclusion about redistribution of generated Windows TTS output. Retain the sidecar and obtain any required internal artifact-store/rights-clearance authorization before treating a generated binary as a release fixture. The artifacts still need the required x64 and ARM64 probe reports; generation alone is not evidence of extraction, cleanup, final-VTT behavior, or release readiness.

## Opt-in extractor evidence

When the rights-cleared binary artifacts are available locally, run the development-only [Windows media integration probe](../tools/WinBulkTranscript.MediaIntegrationProbe/README.md):

```powershell
dotnet run --project tools/WinBulkTranscript.MediaIntegrationProbe -- `
  --matrix-root C:\fixtures\win-bulk-transcript-media `
  --report artifacts\media-probe\matrix.json
```

The probe directly calls the production `WindowsMediaAudioExtractor`, validates its returned PCM representation, and records temporary-WAV ownership/cleanup evidence. It reports missing fixture files as failures rather than assuming they exist. It does not create a final VTT or exercise the coordinator, so preserve the matrix's separate no-final-VTT assertion in batch/workflow integration evidence.

## Opt-in workflow evidence

Use the [end-to-end workflow integration probe](../tools/WinBulkTranscript.WorkflowIntegrationProbe/README.md) for the matrix's separate final-VTT and cancellation assertions:

```powershell
dotnet run --project tools/WinBulkTranscript.WorkflowIntegrationProbe -- `
  --input-root C:\fixtures\win-bulk-transcript-media\valid-inputs `
  --output-root artifacts\workflow-probe\matrix-output `
  --report artifacts\workflow-probe\matrix-success.json
```

Run its explicit cancellation and injected-recognizer-failure scenarios with a disposable output root as documented by the tool. The reports validate header-bearing committed VTTs, no newly left-over temporary WAV/VTT files, and preservation of sentinel final outputs on the selected failure/cancellation paths. Repeat the evidence on x64 and ARM64; no report is a substitute for the binary fixture provenance or a clean-machine release test.
